# StepCap — Guide Me (พาทำทีละขั้นบนจอจริง)

สถานะ: ผู้ใช้อนุมัติแล้ว (2026-10-17) · สร้างแล้วบน branch feat/guide-me · **ผู้ใช้ทดสอบผ่าน (2026-10-17)** · ต่อจากตัวติดตั้ง (PR #8)

## 1. ที่มาและเหตุผล

คู่มือของ StepCap ตอนนี้ต้องอ่านแล้วสลับไปทำเองในโปรแกรมจริง
Guide Me ทำให้คนที่ไม่เคยทำงานนั้นเปิดคู่มือแล้วกด "พาทำ" ได้
จากนั้นโปรแกรมจะชี้เป้าบนจอจริงให้ทีละขั้น และไปขั้นถัดไปเองเมื่อคลิกโดนเป้า
ต้นแบบคือ Guide Me ของ Scribe เวอร์ชันเดสก์ท็อป (แผงด้านข้างมีการ์ดของแต่ละขั้น ขั้นปัจจุบันขยายพร้อมรูป และมีปุ่ม Prev/Next)

**สิ่งที่ถือว่าสำเร็จ:** ผู้ใช้อัดคู่มือใหม่ แล้วย้ายหรือย่อขยายหน้าต่างโปรแกรมเป้าหมาย
กด "พาทำ" แล้วกรอบไฮไลต์ยังขึ้นตรงปุ่มที่ถูกต้อง และคลิกตามจนจบคู่มือได้โดยไม่ต้องกด "ถัดไป" ในขั้นที่เป็นการคลิก

## 2. สิ่งที่ผู้ใช้ตัดสินแล้ว

1. **วิธีหาเป้า:** ใช้ UIA เป็นหลัก ตอนอัดให้เก็บ exe, ชื่อหน้าต่าง, จุดที่คลิกเทียบกับมุมหน้าต่าง,
   และ UIA `name` / `control type` / `AutomationId` ตอนพาทำให้หาหน้าต่างจาก exe ก่อน แล้วหา element
   โดยใช้ AutomationId ถ้าไม่มีหรือไม่เจอให้ใช้ name+type แล้วไฮไลต์กรอบของ element ที่เจอ
   ถ้าหา element ไม่เจอให้ใช้มุมหน้าต่างบวกจุดที่เก็บไว้แทน
2. **คู่มือเก่า** (ไม่มีข้อมูลใหม่): ไฮไลต์ตาม x/y ของ marker บนจอที่เลือกไว้ในการตั้งค่าตอนอัด
   (ค่าเริ่มต้นคือจอหลัก) และในแผงเขียนกำกับว่า "ตำแหน่งโดยประมาณ" ถ้าคลิกในวงนี้ก็ไปขั้นถัดไปเองเหมือนคู่มือใหม่
   ไม่ต้องแปลงไฟล์เก่า
3. **ไปขั้นถัดไป:** ไปเองเมื่อคลิกในกรอบเป้า (ใช้ hook เมาส์ทั้งระบบ แค่ดู ไม่บล็อก และการคลิกยังส่งถึงโปรแกรมจริงตามปกติ)
   หรือกดปุ่ม "ถัดไป" / "ย้อนกลับ" เองได้ทุกเมื่อ
4. **ขั้นที่ไม่ใช่การคลิก** (พิมพ์ / คีย์ลัด / โน้ต): แสดงข้อความของขั้นในแผง ข้อความที่ถูกปิดบังไว้ก็แสดงแบบปิดบังเหมือนเดิม
   **เปลี่ยนหลังผู้ใช้ลองจริง (2026-10-17):** ไปขั้นถัดไปเองเมื่อทำตรงกับที่อัดไว้
   - พิมพ์: เมื่อข้อความที่พิมพ์ (นับ Backspace) ลงท้ายตรงกับที่อัด และถ้าตอนอัดกด Enter/Tab ปิดท้าย ต้องกดปุ่มนั้นด้วย
   - กดปุ่มเดี่ยว (Enter, ลูกศร ...) / คีย์ลัด: เมื่อกดปุ่มหรือคีย์ผสมนั้น
   - รหัสผ่าน, ข้อความที่ถูกปิดบัง, คู่มือที่อัดก่อนหน้า: เมื่อกด Enter หรือ Tab (คีย์ลัดของคู่มือเก่า: คีย์ผสมใดก็ได้)
   - ตอนอัดเก็บ `expect` ต่อขั้น: `typed` (เฉพาะข้อความที่ไม่ถูกปิดบัง) / `ending` / `key` / `keys` — ไม่เก็บรหัสผ่านหรือข้อความที่ถูกปิดบัง
   - โน้ตยังต้องกด "ถัดไป" เอง กด "ถัดไป" เองได้ทุกขั้นเหมือนเดิม
5. **ทางเข้า:** ปุ่ม "พาทำ" ที่แถบหัวของหน้าดูคู่มือเท่านั้น ไม่ใส่ใน tray
6. **เจอหน้าต่างแต่ไม่เจอปุ่ม:** แสดงวงกลมที่ตำแหน่งสำรอง (มุมหน้าต่างบวกจุดที่เก็บไว้) และการ์ดเขียนว่า "ตำแหน่งโดยประมาณ"
   คลิกในวงนี้ก็ไปขั้นถัดไปเอง ระหว่างนั้นระบบยังลองหาปุ่มจริงต่อ ถ้าเจอก็เปลี่ยนเป็นกรอบพอดีปุ่ม
   **หาหน้าต่างไม่เจอเลย** (เช่น โปรแกรมยังไม่เปิด): การ์ดของขั้นขึ้นข้อความ
   "หาเป้าหมายไม่เจอ เปิด {app} ให้ตรงกับหน้านี้ก่อน" และยังมีรูปของขั้นให้ดู
   ระบบลองหาใหม่ทุก ~1 วินาที เจอเมื่อไหร่ก็ไฮไลต์เลย และกด "ถัดไป" ข้ามได้เสมอ
7. **ถ้า marker ถูกลากในตัวแก้รูป:** ยึดข้อมูล UIA ไม่สนตำแหน่ง marker ที่ถูกลาก
8. **แผงด้านข้าง:** ลอยอยู่บนสุดชิดขอบขวาของพื้นที่ทำงาน (ไม่ทับ taskbar) **ไม่จองพื้นที่จอ**
   กว้าง 400px ที่ scale 100% (เดิม 360 ผู้ใช้ขอรูปใหญ่ขึ้น) และกว้างขึ้นตาม scale ของจอ ถ้ากรอบเป้าหมายอยู่ใต้แผง แผงจะย้ายไปชิดซ้ายเอง
   อยู่บนจอเดียวกับหน้าต่างเป้า ถ้าหาไม่เจอให้อยู่บนจอหลัก
   (ผู้ใช้เปลี่ยนจาก AppBar หลังลองใช้จริง 2026-10-17: การจองพื้นที่ทำให้ไอคอนบนเดสก์ท็อปถูกจัดใหม่และไม่ย้ายกลับ)
9. **ในแผง** (หน้าตาตาม Scribe):
   - หัวแผงมีชื่อคู่มือกับปุ่มปิด ✕
   - ถัดลงมาเป็นรายการทุกขั้นแบบการ์ด ขั้นปัจจุบันขยาย มีเลขขั้น ข้อความ และรูปตัวอย่างที่ผ่านครอป วาด และปิดบังข้อมูลแล้ว
     ส่วนขั้นอื่นแสดงบรรทัดเดียว
   - รูปมีปุ่มแว่นขยาย (หรือกดที่รูป) สลับระหว่างภาพเต็มกับซูม 1/3 ของภาพรอบจุดคลิก ระบบจำว่าเลือกแบบไหนไว้แล้วใช้ต่อในขั้นถัดไป
     (ผู้ใช้ขอหลังลองใช้จริง: รูปเต็มจอในแผงเล็กเกินไป)
   - กดการ์ดเพื่อกระโดดไปขั้นนั้นได้ และรายการเลื่อนตามขั้นปัจจุบันเอง
   - ด้านล่างมีปุ่ม "ย้อนกลับ" / "ถัดไป"
   - จบขั้นสุดท้ายแล้วขึ้น "เสร็จแล้ว" พร้อมปุ่มปิด
10. **หน้าต่างหลัก:** ย่อลงตอนเริ่มพาทำ และเปิดกลับที่หน้าคู่มือเดิมตอนปิดแผง
    ระหว่างพาทำเริ่มอัดไม่ได้ (ทั้งปุ่มในแอป, tray และคีย์ลัด)
11. **ไฮไลต์บนจอ:** กรอบสี่เหลี่ยมมุมมนสี `--accent` (#fb923c) หนา 3px ล้อมรอบ element ไม่มีแอนิเมชัน
    คลิกทะลุได้ และไม่ติดในภาพหน้าจอ ถ้าใช้ตำแหน่งสำรองหรือเป็นคู่มือเก่า ให้ใช้วงกลมขนาดเท่า marker แทน
    ถ้าใช้ตำแหน่งสำรองแต่ที่จุดนั้นมีปุ่มของโปรแกรมเดียวกัน ให้ใช้กรอบของปุ่มนั้นทั้งปุ่ม (ทั้งวาดและนับการคลิก)
    **ข้อจำกัด:** Start menu และช่องค้นหาของ Windows อยู่ในชั้นที่โปรแกรมทั่วไปวาดทับไม่ได้ กรอบจึงมองไม่เห็นบนเมนูเหล่านี้
    แต่การคลิกยังนับได้ (ถ้าจะวาดทับต้องใช้ UIAccess ซึ่งต้องเซ็นใบรับรองและติดตั้งใน Program Files)

## 3. ข้อมูลที่ต้องเก็บเพิ่มในคู่มือ

ตอนนี้ `_write_guide` ทิ้ง `app`/`exe` ของแต่ละขั้น และ name/type ของ UIA ก็ไม่ได้เก็บเลย
ขั้นที่เป็นการคลิกในคู่มือใหม่ให้มีฟิลด์เพิ่ม (ชื่อฟิลด์ให้ผู้สร้างเลือก) ดังนี้:

| ข้อมูล | ไว้ทำอะไร |
|---|---|
| ชื่อไฟล์ exe (เก็บแค่ชื่อไฟล์ ไม่เก็บพาธเต็ม) | หาหน้าต่าง และไม่หลุดชื่อบัญชีผู้ใช้ในพาธลงไฟล์ |
| ชื่อหน้าต่าง | ใช้เลือกเมื่อ exe เดียวกันมีหลายหน้าต่าง และใช้แสดงใน "หาไม่เจอ" |
| class ของหน้าต่าง | ใช้เลือกหน้าต่างเมื่อชื่อหน้าต่างเปลี่ยน เช่น ชื่อโฟลเดอร์ ชื่อแท็บ หรือชื่อเอกสาร (เพิ่มตอน final review) |
| จุดคลิกเทียบกับมุมซ้ายบนของหน้าต่าง (หน่วยพิกเซลจริง) | ใช้เป็นตำแหน่งสำรอง |
| UIA name, control type, AutomationId | ใช้หา element |

- **ผู้ใช้ตัดสิน:** รอบนี้เก็บชื่อหน้าต่างและชื่อ element ตามที่อ่านได้ ไม่ปิดบัง (ชื่อปุ่มก็ไม่ได้ปิดบังในข้อความของขั้นอยู่แล้ว)
  การปิดบังชื่อหน้าต่างจะทำในรอบหลัง
- **การตัดสินของผม:** ไม่เก็บ AutomationId ที่ว่างเปล่า
- **การตัดสินของผม:** ถ้า `ElementFromPoint` ได้ตัวหนังสือหรือไอคอนข้างในปุ่ม ให้ไล่ขึ้นไปหา parent ตัวแรกที่กดได้
  (เช่น Button, MenuItem, ListItem, TabItem, Hyperlink, CheckBox, RadioButton, TreeItem, SplitButton, ComboBox, Edit
  หรือ element ที่มี AutomationId) แล้วเก็บตัวนั้นแทน ไม่ไล่ขึ้นเกินหน้าต่าง ถ้าไล่แล้วไม่เจอก็เก็บตัวเดิม
  ข้อความของขั้นยังสร้างแบบเดิมเหมือนทุกวันนี้
- การส่งออก (PDF/Markdown/Word) และหน้าดูคู่มือไม่ใช้ฟิลด์เหล่านี้ และไม่ต้องแสดง
- ลบขั้น ย้ายขั้น หรือทำซ้ำขั้น ข้อมูลต้องติดไปกับขั้นนั้นด้วย (ต้องตรวจว่าการบันทึกจากหน้าดูคู่มือไม่ทิ้งฟิลด์ที่ไม่รู้จัก)

## 4. พฤติกรรมตอนพาทำ

- เริ่มที่ขั้นแรก (**การตัดสินของผม:** ไม่จำว่าค้างไว้ที่ขั้นไหน)
- หาเป้าใหม่ทุก ~0.5–1 วินาที ถ้าหน้าต่างถูกย้าย กรอบก็ตามไป ถ้าหน้าต่างถูกย่อลงหรือหายไปก็ซ่อนกรอบ
  และขึ้นสถานะ "หาไม่เจอ"
- นับว่า "คลิกโดนเป้า" เมื่อปุ่มซ้ายหรือขวาลงในกรอบ (เผื่อขอบไว้เล็กน้อย) และชนิดการคลิกตรงกับขั้น
  ดับเบิลคลิกนับเมื่อคลิกครั้งแรกในกรอบ (**การตัดสินของผม:** ไม่ต้องรอครั้งที่สอง)
  ถ้าคลิกนอกกรอบไม่ต้องทำอะไร
- คลิกบนแผงของ StepCap เองไม่นับ
- ขั้นที่เป็นโน้ตหรือไม่มีเป้า ไม่แสดงกรอบ
- กด ✕ หรือกด Esc ตอนแผงมีโฟกัส จะเลิกพาทำ แล้วเอากรอบ แผง และ hook ออกทั้งหมด
- ถ้าคู่มือถูกลบหรือแก้ไขระหว่างพาทำ ไม่ต้องรองรับ (แผงใช้สำเนาที่โหลดไว้ตอนเริ่ม)

## 5. ทำอย่างไร (ส่วนที่ผมตัดสิน)

- **แผงด้านข้าง:** เป็นหน้าต่าง pywebview ที่สอง โหลด UI เดียวกันผ่าน HTTP server ตัวเดิม (ต้องใช้ token)
  และวาดรูปของขั้นด้วยโค้ดเดียวกับที่ `ui/guide.js` ใช้อยู่ เพื่อให้ครอป เครื่องหมาย และ**การปิดบังข้อมูล**ตรงกับหน้าดูคู่มือ
  ตั้ง `WDA_EXCLUDEFROMCAPTURE` แล้ววางด้วย `SetWindowPos` (บนสุด ไม่แย่งโฟกัส)
- **กรอบไฮไลต์:** เพิ่มลงใน `overlay.py` (tk thread เดิม พื้นโปร่งใส คลิกทะลุ ไม่แย่งโฟกัส และไม่ติดในภาพหน้าจอ)
- **ค้นหา element:** ขยาย `_UIA` ใน `recorder.py` ตอนอัดให้อ่าน AutomationId และตอนพาทำให้ค้นในหน้าต่างเป้า
  (แบบ subtree) และอ่าน `CurrentBoundingRectangle` ต้องรันบน thread ที่มี COM ของตัวเอง เหมือนตัวเดิม
  ถ้ามีหลายตัวที่ตรงเงื่อนไข (เช่น มีปุ่ม "OK" หลายปุ่ม) ให้เลือกตัวที่ใกล้ตำแหน่งที่บันทึกไว้ที่สุด (`FindAll`)
  และข้ามตัวที่กรอบว่างหรืออยู่นอกจอ
- **จอของแผง:** เลือกครั้งเดียวตอนเริ่มพาทำ หลังจากนั้นไม่ย้ายตามหน้าต่างเป้า
- **หาหน้าต่าง:** วนดูหน้าต่างระดับบนสุดที่มองเห็นอยู่ แล้วเลือกตัวที่ชื่อ exe ตรงกัน ถ้ามีหลายตัวให้เลือกตัวที่ชื่อหน้าต่างตรงกัน
  ถ้ายังมีหลายตัวให้เลือกตัวบนสุด
- **พิกัด:** ใช้พิกเซลจริงทั้งหมด (โปรเซสตั้ง DPI aware อยู่แล้ว) ต้องทดสอบบนจอที่ scale ไม่ใช่ 100% และบนหลายจอ
- **hook เมาส์:** ระหว่างพาทำใช้ hook ระดับต่ำตัวเดียวกับ recorder หรือแยกตัวใหม่ก็ได้ แต่ต้องไม่ไปรบกวนการอัด
  (ซึ่งทำพร้อมกันไม่ได้อยู่แล้วตามข้อ 2.10)
- ข้อความใหม่ทุกข้อความต้องผ่าน `tr()` และเพิ่มคำแปลใน `ui/en.json`

## 6. ทดสอบ

- **logic แบบ pure (อัตโนมัติ):** การเลือกหน้าต่างจากรายการ (exe/ชื่อหน้าต่าง), การแปลงตำแหน่งเทียบหน้าต่างเป็นตำแหน่งบนจอ,
  การตัดสินว่าคลิกโดนเป้าไหม, การเลื่อนขั้น (ถัดไป/ย้อนกลับ/กระโดด/จบ), และการเลือกวิธีหาเป้าของคู่มือเก่าเทียบกับคู่มือใหม่
- **การอัด:** `StepBuilder` / `_write_guide` เก็บฟิลด์ใหม่ และไม่เก็บพาธเต็มของ exe
- **การบันทึกจากหน้าดูคู่มือ:** ฟิลด์ใหม่ยังอยู่หลังแก้ข้อความหรือย้ายขั้น
- **UI:** ปุ่ม "พาทำ" มีในหน้าดูคู่มือ และแผงพาทำโหลดได้ทั้งโหมดไทยและ English (`test_english.py`) โดยไม่มีภาษาไทยหลุด
- **UIA กับหน้าต่างจริง:** เปิดหน้าต่างทดสอบของเราเอง (tk) แล้วหาปุ่มในหน้าต่างนั้นด้วย UIA และได้กรอบที่ถูกต้อง
  **ห้ามส่งคลิกหรือพิมพ์**จริงบนเดสก์ท็อป ให้จำลองเหตุการณ์คลิกด้วยการเรียกฟังก์ชันตรง
- ทุกเทสต์ตั้ง `STEPCAP_STORAGE` ไปที่โฟลเดอร์ชั่วคราว และชุดทดสอบเดิมต้องผ่านทั้งหมด
- **ผู้ใช้ทดสอบเอง:** อัดคู่มือใหม่ในโปรแกรมจริง ย้ายและย่อขยายหน้าต่าง แล้วลองพาทำ ลองบนจอที่ scale ไม่ใช่ 100%
  และบนจอที่สอง (ถ้ามี) ลองคู่มือเก่า 1 อัน และลองกรณีที่ยังไม่ได้เปิดโปรแกรม

## 7. ไม่ทำ (non-goals)

- (เดิม: ตรวจจับการพิมพ์หรือคีย์ลัด — ย้ายไปทำแล้วตามข้อ 2.4)
- เปิดโปรแกรมเป้าให้อัตโนมัติ หรือคลิก/พิมพ์แทนผู้ใช้
- ทางเข้าจาก tray, จำขั้นที่ค้างไว้, สถิติการใช้งาน
- แก้คู่มือจากในแผงพาทำ
- ตรวจว่า marker ถูกลากไปจากจุดเดิมแล้ว
- ทำให้รองรับหน้าเว็บในเบราว์เซอร์เป็นพิเศษ (ได้เท่าที่ UIA ของเบราว์เซอร์ให้มา)

## 8. สิ่งที่ถือว่าล้มเหลวแม้จะทำงานได้

- กรอบไฮไลต์ไม่ตรง element บนจอที่ scale ไม่ใช่ 100% หรือบนจอที่สอง
- กรอบหรือแผงไปติดในภาพหน้าจอ หรือแผงบังเป้าของหน้าต่างที่ขยายเต็มจอ
- คลิกของผู้ใช้ไม่ถึงโปรแกรมจริง หรือ StepCap แย่งโฟกัสระหว่างที่ผู้ใช้กำลังทำงาน
- รูปในแผงแสดงข้อมูลที่ถูกปิดบังไว้
- เลิกพาทำแล้ว แต่กรอบหรือ hook ยังค้างอยู่ หรือไอคอนบนเดสก์ท็อปถูกจัดใหม่
- มีพาธเต็มหรือชื่อบัญชีผู้ใช้หลุดลง `guide.json`
- เทสต์ไปคลิกหรือพิมพ์บนเดสก์ท็อปจริง หรือไปแตะคู่มือจริง

## 9. ให้ผู้สร้างตัดสินเอง

- ชื่อฟิลด์ใน `guide.json` และว่าจะเก็บเป็นก้อนย่อยหรือไม่
- ความถี่ในการหาเป้าใหม่ ระยะเผื่อของกรอบ และขนาดฟอนต์/ระยะห่างในแผง (ยึดตาม DESIGN.md)
- จะแยกไฟล์ Python ใหม่สำหรับ Guide Me หรือไม่ (เช่น `guideme.py`) และวิธีที่แผงคุยกับ backend
- ถ้อยคำในแผง
